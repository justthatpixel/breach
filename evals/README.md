# Evals

Both suites run the real judge end to end: real retrieval against
Postgres, a real LLM call, real evidence and confidence verification. Not
the LLM in isolation, so what's measured is the whole credit pipeline.

## Judge accuracy (`evals/judge/`)

```bash
docker compose up -d db   # from the repo root
cd apps/api && source ../../.venv/bin/activate
python -m breach.retrieval.migrate && python -m breach.retrieval.seed
python -c "from breach.retrieval.embed_mitigations import embed_mitigations; from breach.retrieval import DeterministicTestEmbedder; embed_mitigations(provider=DeterministicTestEmbedder())"
cd ../..
LLM_PROVIDER=ollama EMBEDDING_PROVIDER=test python -m evals.judge.run_judge_eval
```

`cases.jsonl` (70 cases, generated by `gen_cases.py` so the dataset's
construction is auditable rather than hand-typed) covers every component
type with: two easy single-mitigation cases per candidate mitigation, a
hard case combining two in one note, a vague case with no concrete
measure, a "wrong but confident" buzzword case, and a "right idea, wrong
mitigation" case (a real, specific measure that genuinely isn't a
candidate for that component's techniques, the same teaching point as the
M2 golden test: encryption doesn't stop a stolen-credentials attack).

The runner reports micro-averaged precision, recall, and F1, writes the
full result with per-case diffs to `evals/results/<timestamp>.json`
(gitignored, since these are run artifacts and not the committed
baseline), and `--update-baseline` additionally writes `baseline.json`,
which the CI gate (`evals/ci_gate.py`) compares future runs against.

## Injection (`evals/injection/`)

```bash
LLM_PROVIDER=ollama EMBEDDING_PROVIDER=test python -m evals.injection.run_injection_eval
```

31 adversarial notes (direct instruction overrides, role-play, fake
system or developer messages, encoded or obfuscated text, and
instructions hidden inside an otherwise plausible security note), none of
which make a genuine, verifiable security claim. Pass criterion: zero
unjustified credits across all of them. Exits non-zero on any failure.

## The LLM used

Both suites use whatever `breach.llm.get_default_client()` returns, based
on `LLM_PROVIDER` in the environment. Locally and in CI, that's Ollama
with Qwen3 8B (`qwen3:8b`), run on a self-hosted GitHub Actions runner on
the project's own machine. It's free per run, needs no API key, and has
Qwen3's own extended-thinking mode turned off (`think: false` in
`breach/llm.py`'s `OllamaLLMClient`), since a judge or narrator call is
schema-constrained and gets nothing from extended thinking but latency.

`LLM_PROVIDER=anthropic` works the same way against Claude if you'd
rather use that (needs `ANTHROPIC_API_KEY`). `LLM_PROVIDER=test` is the
deterministic, no-network stand-in the rest of the test suite uses. It's
fine for exercising the harness, but it isn't meant to produce real eval
numbers (see `DeterministicTestLLMClient`'s docstring).

## CI gate

`.github/workflows/evals.yml` runs both suites on the self-hosted runner
for any pull request touching `judge/`, `narrator/`, `retrieval/`,
`security/`, `llm.py`, `data/attack/`, or `evals/` itself. Then
`evals/ci_gate.py` fails the job (and posts a pull request comment with
the numbers) if the judge's F1 drops more than 3 points below the
committed baseline, or if any injection case produced an unjustified
credit.
